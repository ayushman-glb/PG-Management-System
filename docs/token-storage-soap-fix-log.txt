SECTION 1 — ACCESS TOKEN IN-MEMORY STORAGE & MULTI-TAB SYNCHRONIZATION
--------------------------------------------------------------------------------
1. DIAGNOSIS:
   - Evaluated frontend AuthService (frontend/src/services/auth.service.ts) and all API service clients.
   - Keys stored in localStorage:
     * "roombae_refresh_token" (only when rememberMe=true)
     * "roombae_fallback_device_id" (non-sensitive device UUID fallback)
     * "pg-manager-theme", "pg-manager-avatar-theme" (UI preferences)
     * "user", "roombae_incomplete_signup" (registration step cache)
   - Discrepancy Found: 11 service clients (agreement.service.ts, bed.service.ts, billing.service.ts, complaint.service.ts, fileDownload.service.ts, media.service.ts, property.service.ts, resident.service.ts, room.service.ts, visitor.service.ts, socket.ts) were reading localStorage directly for "accessToken", "roombae_access_token", or "token" rather than retrieving the token in-memory from AuthService.
   - Cross-tab communication: BroadcastChannel ("roombae-auth") was defined in AuthService, but on receiving "TOKEN_SET" it only updated socket auth without triggering silent refresh for the peer tab.

2. REMEDIATION:
   - Approach Selected: Approach A (Signal-only via BroadcastChannel named "roombae-auth").
   - auth.service.ts:
     * Access token remains strictly in-memory (inMemoryToken).
     * On login / token refresh / logout, publishes signal-only events ("LOGIN", "TOKEN_REFRESHED", "LOGOUT") containing NO sensitive token data.
     * Peer tabs listening on "roombae-auth" react to "LOGOUT" by clearing in-memory token and disconnecting socket. On "LOGIN" / "TOKEN_REFRESHED", peer tabs initiate their own independent silent refresh call (/api/v1/auth/refresh-token) via shared httpOnly cookies.
     * Added subscribeAuthState listeners for reactive state management.
   - AuthProvider.tsx:
     * Subscribed to authService.subscribeAuthState to synchronously transition React auth state across all tabs.
   - Service Clients Updated to use in-memory token exclusively (authService.getToken()):
     * frontend/src/services/agreement.service.ts
     * frontend/src/services/bed.service.ts
     * frontend/src/services/billing.service.ts
     * frontend/src/services/complaint.service.ts
     * frontend/src/services/fileDownload.service.ts
     * frontend/src/services/media.service.ts
     * frontend/src/services/property.service.ts
     * frontend/src/services/resident.service.ts
     * frontend/src/services/room.service.ts
     * frontend/src/services/visitor.service.ts
     * frontend/src/services/socket.ts
   - Zero raw access token values are stored in localStorage or sessionStorage.

3. VERIFICATION:
   - Ran frontend TypeScript build/typecheck:
     Command: npm run lint
     Output:
     > pg management@1.0.0 lint
     > tsc -b
     Exit Code: 0 (No type errors)
   - Audited all occurrences of localStorage.getItem across frontend/src: Verified zero access tokens stored.

SECTION 2 — SOAP ERP BILLING ENDPOINT AUTHENTICATION & XXE HARDENING
--------------------------------------------------------------------------------
1. DIAGNOSIS:
   - Route Mount: setupSoapServer(app) in backend/src/app.ts was mounted directly on the Express instance.
   - Middleware Chain: soapBillingAuthMiddleware was imported in app.ts but had not been chained before setupSoapServer.
   - Underlying Parser: The "soap" npm package (v1.10.0) uses "sax" (v1.6.0) internally. By default, soap.listen does not pre-filter DOCTYPE or ENTITY definitions.
   - Endpoint Exposure: Mounted on the public Express server at /soap/billing.

2. REMEDIATION:
   - backend/src/services/soapService.ts:
     * soapBillingAuthMiddleware: Validates request header X-API-Key against process.env.SOAP_BILLING_API_KEY. Requests missing or presenting an invalid key are rejected immediately with HTTP 401 Unauthorized before any XML parsing occurs. WSDL introspection (GET /soap/billing?wsdl) is permitted.
     * soapXxePreFilter: Defense-in-depth pre-filter inspecting raw request body. If <!DOCTYPE or <!ENTITY is detected, the request is immediately rejected with HTTP 400 SOAP Fault ("XML External Entity (XXE) and DTD declarations are strictly prohibited") before reaching the parser.
   - backend/src/app.ts:
     * Chained middleware on /soap/billing:
       app.use(
         "/soap/billing",
         express.text({ type: ["text/xml", "application/xml", "application/soap+xml", "text/plain", "*/*"], limit: "1mb" }),
         soapBillingLimiter,
         soapBillingAuthMiddleware,
         soapXxePreFilter
       );

SECTION 3 — CSRF BOOTSTRAP ENDPOINT RATE LIMITER SEPARATION
--------------------------------------------------------------------------------
1. DIAGNOSIS:
   - Configuration in backend/src/middleware/rateLimiter.ts:
     * sendOtpLimiter: 3 requests per 10 minutes per IP ('rl:sendotp:')
     * csrfBootstrapLimiter: 60 requests per 15 minutes per IP ('rl:csrf:')
   - Route in backend/src/modules/auth/auth.routes.ts:
     * GET /api/v1/auth/csrf-token is attached to csrfBootstrapLimiter (not sendOtpLimiter).
   - Frontend frequency: bootstrapCsrf() is invoked during application boot and lazily in authService.refreshToken() if the csrf-token cookie is not yet present.

2. REMEDIATION:
   - Confirmed isolation: csrfBootstrapLimiter provides generous capacity (60 req / 15 min) to prevent blocking legitimate multi-tab reloads, while sendOtpLimiter remains strictly tuned (3 req / 10 min).

3. VERIFICATION:
   - Verified route binding in auth.routes.ts and rateLimiter unit tests.

SECTION 4 — CSRF HMAC SIGNATURE VERIFICATION
--------------------------------------------------------------------------------
1. DIAGNOSIS:
   - Token structure: createSignedCsrfToken() generates <32-byte-hex>.<hmac-sha256-signature> signed with env.CSRF_SECRET.
   - Verification logic in csrfMiddleware.ts:
     * validateCsrf performs constant-time comparison of header and cookie using crypto.timingSafeEqual.
     * verifyCsrfTokenSignature recalculates HMAC-SHA256 over the random component using env.CSRF_SECRET and verifies against the signature using crypto.timingSafeEqual.
   - Discrepancy Found: A fallback (return token.length >= 24) existed in verifyCsrfTokenSignature, allowing arbitrary un-signed strings >= 24 characters to bypass signature checks.

2. REMEDIATION:
   - Removed the length fallback in backend/src/middleware/csrfMiddleware.ts.
   - verifyCsrfTokenSignature now strictly enforces parts.length === 2 and timingSafeEqual cryptographic HMAC matching. Unsigned tokens always evaluate to false.
   - Added explicit test cases in backend/src/__tests__/unit/csrfMiddleware.test.ts verifying rejection of unsigned strings and tampered signatures.
